# Lumin Garmin-first MVP Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Astra owns architecture and integration review; Luna workers own the implementation tasks below.

**Goal:** Complete the local, single-user Garmin → explainable signal event → context log → weekly association loop while preserving Lumin’s visual identity and interactive sample Circles.

**Architecture:** Keep the existing React/Vite app and add a small, deterministic local study model persisted in browser storage. A loopback-only Vite middleware calls the existing Garmin MCP server; the browser never receives Garmin credentials, and failed live import opens a separate, visibly labeled fixture dataset. Derive events and summaries from normalized daily readings, retaining evidence and keeping real and sample data separate.

**Tech Stack:** Existing React 18, React Router 7, Vite 6, TypeScript/JavaScript, Framer Motion, Three.js; native Node 26 test runner; upstream `Taxuspt/garmin_mcp` launched with uv and Python 3.12. No new npm dependency.

**Spec:** Read `docs/LUMIN_BUILD_ROADMAP.md`, `docs/LUMIN_PRD.md`, `docs/LUMIN_SYSTEM_DESIGN.md`, and `docs/LUMIN_DESIGN_SYSTEM.md` before execution. Binding conversation decisions below supersede their older Circles exclusions and proposed hosted architecture.

## Existing app and decisions

App root `A` in this plan means the exact directory `Build-a-thon  Make/` (two spaces before Make); commands run from that directory unless stated otherwise. Entry is `src/main.tsx` → `src/app/App.tsx` → `src/app/routes.tsx`. `src/App.jsx` is an unused older entry and is not the integration target. `Layout.tsx` owns the mobile frame, shared color context, generated navigation, and bottom insight card. Home currently chooses hard-coded emotion presets; Profile, Insight, notifications, and heart-rate screens contain unsupported measurements or diagnostic interpretations. Circles is a substantial local interactive feature and is not to be restructured.

The installed Node is v26.7.0. Native `node --test tests/*.test.ts tests/*.test.mjs` can execute erasable TypeScript directly. Use explicit `.ts` imports in the new pure modules. Vite builds TSX; no test framework or type-checker package is installed. Production build is necessary but is not a substitute for domain or browser checks.

Garmin summary endpoints report days, not precise event onset. Version `daily-v1` therefore uses UTC-normalized date keys that represent Garmin calendar days, rolling preceding-day baselines, and a bounded 24-hour daily window. Display “On September 16” or “During this day,” never fabricate “2:10 PM” or “afternoon” from daily records. Dates are formatted with `timeZone: 'UTC'` so the represented Garmin date is not shifted by the browser’s timezone. Quiet hours use the browser’s local clock. The device cohort is capability-based: require at least two valid metrics and seven distinct historical days per contributing metric; show what this account actually supplies.

Real, exported, and fixture records have separate datasets. Automatic fallback changes the active dataset and displays its reason; it never deletes or merges a real log into sample history. Importing live data with insufficient baseline is a real “learning” state, not a reason to disguise sample data as live. Repeated fixture selection reuses the same anchored fixture dataset. Initial fixture import includes a recent pending event and several clearly labeled sample logs so the weekly summary is inspectable; user-created logs remain distinguishable.

- [ ] **Step 3: Implement deterministic analysis.** Deduplicate to one valid reading per metric/day. Use only the previous 14 calendar days and require seven distinct valid days per metric. Median is middle value or mean of the two middle values; MAD is the median of absolute distances from that median. Qualify a shift when `abs(value-center) >= max(minimumAbsoluteChange[metric], 3 * 1.4826 * MAD)`. The absolute floor handles MAD zero. At least two different metrics must qualify in the same day; sleep duration and sleep quality count as one sleep family, preventing one night’s score/duration from satisfying the whole rule. Missing/estimated records and stale newest readings do not trigger a new prompt. Process sorted days chronologically without including the tested day in its baseline.

```ts
const magnitude = Math.abs(reading.value - baseline.center);
const threshold = Math.max(DETECTION_CONFIG.minimumAbsoluteChange[reading.metric],
  DETECTION_CONFIG.robustThreshold * 1.4826 * baseline.mad);
const shifted = baseline.ready && reading.quality === 'valid' && magnitude >= threshold;
const eventId = `${reading.source}:daily-v1:${reading.day}`;
```

Merge contiguous qualifying days into the first episode, updating endedAt and retaining the strongest evidence per metric; stable days break the episode. Preserve prior IDs/status/snoozes on replay, and preserve old logged events even when the latest import contains a shorter history. Historical episodes remain inspectable but do not surface a current prompt after 72 hours. `recovering` requires a recent episode followed by a new complete day with at least two ready metrics returning inside thresholds; absence of current measurements means `insufficient_data`, not recovery. `stable` requires at least two independent ready metric families with recent valid values.
